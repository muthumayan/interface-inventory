Network-wide Interface Inventory

Abstract

This document defines a YANG data model for a network-wide inventory of physical and logical interfaces, organized by network element. The model provides interface attributes, operational state, and layering relationships, with correlations to network inventory and topology data.¶

1. Introduction

Network operators and management systems need a consistent inventory of physical and logical interfaces across network elements. Such an inventory supports per-device retrieval of interface attributes and state, as well as correlation with network inventory and topology models.¶

An SDN controller can expose this inventory to northbound clients, such as higher-level controllers and automation systems, to support network-wide operations.¶

RFC 8343 [RFC8343] defines interface data, including operational state and interface-layering relationships, for a server. The IVY network inventory model [IVY-INVENTORY] describes network elements and their components, while RFC 8345 [RFC8345] and the IVY inventory topology model [IVY-TOPOLOGY] describe topology and its relationship to inventory. These models provide complementary information.¶

This document defines a network-wide interface inventory organized by network element. It reuses RFC 8343 interface data and provides correlations to network inventory and topology. Sections 5 and 6 describe the data model, Section 7 describes operations, and Appendix A provides a worked example. Discovery and reconciliation of the underlying data are implementation-specific.¶

3. Problem Statement

A SDN controller may collect interface data from multiple network elements. RFC 8343 provides an interface model for a network-element, including interface state and layering. The controller also keeps an inventory of all network elements and their physical component inventory. Depending on the layer in which the controller operates it also keeps track of the topological view of the network (L1, L2 or L3).¶

The IVY inventory model [IVY-INVENTORY] describes the network-element inventory, while RFC 8345 [RFC8345] and the IVY inventory topology model [IVY-TOPOLOGY] describe topology and its relationship to inventory. While these models are self-sufficient in mapping topology to physical inventory, they lack the relationship that ties the packet forwarding construct (a.k.a interfaces) to the physical inventory.¶

A northbound client (like a multi-domain controller or an OSS) would need to correlate information from several datasets (inventory, topology, interfaces) in order to reconstruct a network wide view.¶

As an example, a controller can learn from the RFC 8345 topology model which link connects two network devices. If that link is realized as a link aggregation group (LAG) and the link degrades (for example, due to loss/errors on one member), troubleshooting typically requires identifying the member interfaces of the LAG on each device. A controller may already collect the LAG and member-interface relationships while building its topology view, but RFC 8345 does not provide a device-scoped interface inventory (with layering) that can be correlated directly to the topology termination points.¶

This document's proposed model allows the controller to expose that per-device interface inventory and its correlations northbound, so that clients can navigate from a topology link to the underlying per-device member interfaces.¶

As another example, a northbound performance management system may want to correlate the topological state with performance metrics from specific interfaces. Mere knowledge of physical ports and of termination points may not suffice when LAG or VLAN interfaces are involved.¶

This proposed model aggregates interface information from multiple network devices and presents them contextually combining inventory and topological references. The model's completeness and accuracy depend on the data available to the server and on the controller's discovery and reconciliation mechanisms.¶

4. Relationship to Existing Work

RFC 8343 [RFC8343] Section 3.3 ("Interface Layering") already defines the generic mechanism this document needs: two read-only leaf-lists, "higher-layer-if" and "lower-layer-if", present on every "/interfaces/interface" entry, explicitly described as the YANG equivalent of the IF-MIB "ifStackTable" (RFC 8343 Section 4). A LAG's members populate the LAG's "lower-layer-if"; each member's "higher-layer-if" points back at the LAG. A VLAN sub-interface's "lower-layer-if" points at its parent physical interface. This document does not redefine LAG or VLAN semantics; it relies entirely on RFC 8343 Section 3.3 for interface stacking.¶

RFC 8528 [RFC8528] ("YANG Schema Mount") defines a mechanism for attaching a schema tree at a mount point. Appendix A illustrates device/LNE-scoped mounted data, but does not prescribe a device key or require one mount per device. This proposal chooses that organization as a data-model design. It uses separate parent and mounted modules. RFC 8528 confines paths in a mounted schema to the mount jail; therefore the mounted augmentation represents cross-model inventory/topology identifiers as strings rather than leafrefs into parent-schema data. A server may use shared-schema parent-reference metadata for XPath evaluation, but this proposal does not require it. This document does not change RFC 8345, RFC 8346, RFC 8944, or the IVY drafts.¶

5. Data Model Overview

5.1. Design Summary

  • "network-interface-inventory/device" is keyed by "ne-ref", a leafref into the IVY "network-element" list -- the same device identifier already used by inventory, so no new device identity scheme is introduced.¶

  • Each "device" list entry is an RFC 8528 mount point labeled "interfaces-root", under which the server exposes a mounted "ietf-interfaces:interfaces" subtree. The server advertises the mounted module set in schema-mount/YANG Library data.¶

  • Every "if:interface" entry in that mounted subtree is augmented (Section 6) with:¶

    • an "inventory-ref" carrying the IVY port component identifier, when one is known, within the network element identified by the enclosing device's "ne-ref"; and¶

    • zero or more "topology-ref" entries carrying string identifiers for the RFC 8345 network/node/termination-point views corresponding to the interface. Interfaces may exist without participating in any topology view; in that case, the "topology-ref" list is not present; and¶

    • a "vlan-id" convenience leaf populated from the corresponding RFC 8944-style topology attributes, so a client does not have to dereference "topology-ref" just to read a VLAN tag. RFC 8343 can represent VLAN subinterfaces and their layering relationships, but it does not define a standard leaf for the VLAN tag value itself.¶

    • IP addressing and per-family MTU are represented using RFC 8344 (ietf-ip) within the mounted schema set, rather than being duplicated as additional augmentation leaves.¶

  • "higher-layer-if" and "lower-layer-if" are NOT redefined; they are inherited unmodified from RFC 8343. The server populates this operational view from device/interface data and available LAG/VLAN relationships; the discovery and reconciliation mechanism is implementation-specific.¶

The following illustration shows the hierarchy and example correlations. Device identifiers are abbreviated, and RouterX represents another network element. Arrows indicate relationships, not data containment.¶

network-interface-inventory

+-- device [ne-ref = RouterA] [mount point: interfaces-root]
|   +-- interfaces ...
|
+-- device [ne-ref = RouterB] [mount point: interfaces-root]

|       +-- interface [Bundle-Ether10]
|       |   +-- lower-layer-if --> TenGigE0/1/0/0

5.3. Augmentation Overview

The mounted interface augmentation provides three categories of information:¶

  • Correlation identifiers to connect per-device interface entries to inventory and topology views.¶

  • Convenience leaves derived from topology data, so clients do not need to dereference topology termination points to retrieve a VLAN tag value. RFC 8343 can represent VLAN subinterfaces, but does not define a standard leaf for the VLAN tag value.¶

  • An optional controller-provided annotation for information that is specific to the controller's inventory view.¶

  • Most common interface attributes are already addressed in RFC 8343. There are other interesting interface attributes such IP addressing and IPv4/IPv6 MTU. These are provided by RFC 8344 (ietf-ip) which in turn builds on RFC 8343.¶

Normative definitions for the augmentation are in the YANG modules in Section 6. Examples are in Appendix A. Informative comparisons and mappings are in Appendices B and C.¶

   +=======================+==============================+
   | Node(s)               | Purpose                      |
   +=======================+==============================+
   | inventory-ref         | Correlate to inventory port  |
   | topology-ref          | Correlate to topology TP(s)  |
   | vlan-id               | Convenience VLAN tag value   |
   | controller-annotation | Controller annotation        |
   +================+=====================================+
¶

6. YANG Modules

The model is split to respect RFC 8528 mount-jail semantics. The parent module is loaded in the management system's parent schema. At each mount point, the server advertises a mounted schema set that includes ietf-interfaces, ietf-ip, and device-interface-attributes.¶

The same mounted module set MAY be shared by all devices when their schemas are identical. The server MUST publish the applicable mount-point schema through RFC 8528 schema-mount data and the YANG Library mechanism (RFC 8525).¶

The mounted augmentation contains no leafref into the parent inventory or topology trees. Its cross-model correlation values are strings: RFC 8528 confines mounted paths to the mount jail unless a server configures shared-schema parent-reference metadata. This proposal does not require parent-reference metadata.¶

6.2. Mounted augmentation: device-interface-attributes

<CODE BEGINS> file "device-interface-attributes@2026-11-24.yang"¶

module device-interface-attributes {
  yang-version 1.1;
  namespace "urn:example:ns:yang:device-interface-attributes";
  prefix "edia";

  import ietf-interfaces  { prefix if; }

  organization "TBD";
  contact "TBD";

  description
    "Read-only augmentation of a mounted ietf-interfaces schema for
     device-scoped interface inventory. This module is intended to be
     included in the mounted schema set at the interfaces-root mount point
     defined by inventory-network-interfaces.

     RFC 8528 confines a mounted schema to its mount jail. Therefore,
     inventory-ref and topology-ref values are correlation identifiers
     represented as strings; the mounted module does not use leafrefs
     that cross into the parent inventory or topology schema.";

  revision 2026-11-24 {
    description
      "-04 revision. Removes ip-address, mtu, and layer-rate augmentation
       leaves; relies on RFC 8344 (ietf-ip) for interface IP addressing
       and per-family MTU within the mounted schema set, and relies on
       RFC 8343 if:speed for interface capacity.";
    reference "draft-ragalla-network-interface-inventory";
  }

  revision 2026-10-29 {
    description
      "-03 revision. Removes current-alarm-severity and alarm-ref from
       the mounted interface augmentation. All remaining augmentation
       data is operational/read-only; cross-mount correlations use
       string identifiers to respect the RFC 8528 mount-jail boundary.";
    reference "draft-ragalla-device-interface-inventory-03";
  }

  revision 2026-10-13 {
    description
      "Initial -02 mounted-interface augmentation. All augmentation
       data is operational/read-only. Cross-mount correlations use
       string identifiers to respect the RFC 8528 mount-jail boundary.";
    reference "draft-ragalla-device-interface-inventory-02";
  }

  grouping topology-ref {
    description
      "Reference to a termination point in an RFC 8345 topology view.
       The identifiers are strings because the referenced topology
       data may be outside the mounted schema.";

    leaf network-ref {
      type string;
      mandatory true;
      description "RFC 8345 network-id.";
    }
    leaf node-ref {
      type string;
      mandatory true;
      description "node-id within network-ref.";
    }
    leaf tp-ref {
      type string;
      mandatory true;
      description "tp-id within node-ref.";
    }
  }

  grouping inventory-ref {
    description
      "Identifies the inventory port component associated with this
       interface, within the network element identified by the
       enclosing device's ne-ref. The identifier is a string because
       IVY inventory data may be outside the mounted schema.";

    leaf port-ref {
      type string;
      description
        "IVY component-id of the physical port, when known, scoped
         to the network element identified by the enclosing device's
         ne-ref. This leaf identifies a directly associated physical
         port. A link aggregation interface has no port-ref; its
         physical ports can be identified by following its
         lower-layer-if entries to member interfaces and reading
         their port-ref values, when the server reports those
         relationships and correlations. This string does not enforce
         the existence of the referenced inventory component.";
    }
  }

  augment "/if:interfaces/if:interface" {
    description
      "Adds read-only inventory/topology correlations and commonly
       needed interface attributes to the mounted RFC 8343 interface
       list. IP addressing and per-family MTU are represented using
       RFC 8344 (ietf-ip) when that module is included in the mounted
       schema set. The base ietf-interfaces module remains unchanged.";

    container inventory-ref {
      config false;
      description
        "Correlation to a physical port component, if one is known.";
      uses inventory-ref;
    }

    list topology-ref {
      config false;
      key "network-ref node-ref tp-ref";
      description
        "Zero or more topology termination points corresponding to
         this interface. Interfaces may exist without participating in
         any topology view; in that case, this list is not present.
         An interface represented in multiple topology layers has one
         entry per layer/view.";
      uses topology-ref;
    }

    leaf vlan-id {
      config false;
      type uint16 { range "1..4094"; }
      description
        "Outer VLAN identifier (VLAN tag value) when applicable. This is
         a convenience attribute: RFC 8343 can represent VLAN
         subinterfaces, but does not define a standard leaf for the VLAN
         tag value itself; implementations typically derive it from L2
         configuration and/or topology attributes. When the interface is
         not VLAN-tagged (for example, a physical parent interface), this
         leaf is not present.";
      reference
        "RFC 8944; openconfig-vlan single-tagged vlan-id";
    }
    leaf controller-annotation {
      config false;
      type string;
      description
        "Optional controller-provided annotation for the interface.";
    }
  }
}

7. RESTCONF Operations

These examples use the RESTCONF URI form defined by RFC 8040 for a resource beneath a schema-mount point. They assume the parent and mounted schemas described in Section 6 are advertised by the server through schema-mount/YANG Library data. Implementations that do not expose RESTCONF may provide equivalent data through another API.¶

7.1. Retrieve All Interfaces on a Device

A client retrieves every interface on a device with a single GET against the mounted interfaces container. URI path key values MUST be percent-encoded when they contain reserved characters:¶

   GET /restconf/data/inventory-network-interfaces:\
       network-interface-inventory/device=RouterB.subdomain1.region3.isp.example.net/\
       ietf-interfaces:interfaces
¶

The response representation is the mounted "ietf-interfaces:interfaces" subtree plus augmentation data. The requested device key supplies the network-element context for any "inventory-ref/port-ref" in that subtree. Appendix A.2 shows a shortened full parent data-tree fixture for context; it is not the literal body of this subtree GET.¶

7.2. Retrieve a Single Interface 

   GET /restconf/data/inventory-network-interfaces:\
       network-interface-inventory/device=RouterB.subdomain1.region3.isp.example.net/\
       ietf-interfaces:interfaces/\
       interface=Bundle-Ether10
¶

7.3. Filtering by Interface Type

RESTCONF does not define generic server-side predicate filtering on list entries. The base operation in this document returns the interface list; RFC 8040 "fields" and "depth" may be used for payload selection. A future revision MAY specify a YANG action or another explicit filter contract for high-interface-count devices; no such action or filter is defined by this revision.¶

7.4. Protocol Buffers Encoding for Streaming Clients

RESTCONF/JSON (RFC 7951) is the canonical encoding for this document's data model, but some clients -- in particular gRPC- based telemetry and streaming consumers -- prefer a typed binary wire format. A non-normative Protocol Buffers (proto3) schema, "inventory-network-interfaces-02.proto", is published alongside this document.¶

Relationship to gNMI. gNMI (gRPC Network Management Interface, gRPC-based model-agnostic subscribe/get for YANG-modeled data) is an established streaming option for this data model [GNMI]. Clients may subscribe to the mounted ietf-interfaces subtree with gNMI; the service-specific proto is an alternative for clients that want strongly typed messages without gNMI's generic "TypedValue" and path-oriented API. It is optional and does not replace gNMI or the RESTCONF operations in Sections 7.1-7.3.¶

The proto schema defines:¶

  • "Interface", "Device", and "DeviceInterfaces" messages that represent data from both YANG modules in Section 6. The proto uses snake_case names and includes helper fields such as "type_name" for IANA values outside its finite enum; the proto comments document the mapping;¶

  • enum types for "InterfaceType", "AdminStatus", "OperStatus", "DuplexMode", "Direction", "ServiceState", and "EventType" corresponding to this module's YANG enumerations;¶

  • a unary "DeviceInterfaceInventory.GetDeviceInterfaces" RPC, equivalent to the RESTCONF GET in Section 7.1;¶

  • a paginated "ListDeviceInterfaces" RPC that returns "ListDeviceInterfacesResponse" with "device" entries plus a "next_page_token", for clients iterating over a very large fleet; and¶

  • a server-streaming "StreamDeviceInterfaceEvents" RPC that pushes a "DeviceInterfaceEvent" (create / update / delete / initial snapshot, with a timestamp and optional "changed_fields") per interface event. For DELETE, "interface" carries the last-known pre-delete snapshot; initial synchronization uses the distinct SNAPSHOT event type.¶

The protobuf schema is informative. Its field naming and helper enum fields are not a normative wire encoding of YANG; the YANG modules in Section 6 are authoritative if the representations differ. Any companion protobuf schema needs to be updated to reflect the removal of the per-interface inventory "ne-ref".¶

8. Security Considerations

The parent device list exposes device identifiers and interface inventory relationships. Implementations MUST apply authorization to both the parent device list and every mounted interface schema. Access control on a parent data node does not by itself establish the same policy for mounted data. Servers MUST configure and test access control for mounted instances in accordance with RFC 8528 and the Network Configuration Access Control Model (NACM, RFC 8341).¶

The YANG augmentation modules defined here are operational/read-only (their added nodes are config false). The mounted ietf-interfaces schema itself contains both configuration and operational-state nodes; this document does not claim that the whole mounted schema is config false. A GET-only facade MUST reject write methods unless a separate write contract and authorization policy are specified.¶

Interface identifiers, topology relationships, and device inventory can be sensitive network information. Implementations SHOULD limit access by user, tenant, and device scope, protect RESTCONF/API transport with TLS, and apply equivalent authorization to streamed events and unary reads.¶

A.1. Example Network and Illustrative Goals

The topology payloads describe the following three-router connectivity. RouterA, RouterB, and RouterC are shorthand for the corresponding *.subdomain1.region3.bt.uk node identifiers in the fixture.¶

RouterB inventory-only ports: TenGigE0/2/0/1 and HundredGigE0/2/0/1 (no topology TP/link).¶

The RouterA-to-RouterB connection has VLAN subinterfaces 100, 200, and 300 over the physical TenGigE port. RouterB and RouterC connect through the Bundle-Ether10 LAG; the two member links are shown below it. RouterA and RouterC have a direct HundredGigE link.¶

The example is intended to illustrate three client tasks:¶

  • navigating from a topology connection to the device interfaces that realize it, including the members of a LAG;¶

  • following interface-layering relationships between a physical interface and its VLAN subinterfaces; and¶

  • distinguishing a known inventory port from a topology termination point, as demonstrated by RouterB's inventory-only ports.¶

These relationships can be represented without requiring a client to reconstruct them by joining unrelated datasets. The mounted interface tree provides the per-device interface state and layering, while the augmentation supplies the inventory and topology correlations.¶

RouterB's interfaces are represented as follows in the source inventory and topology data:¶

  • TenGigE0/2/0/0: physical interface in the physical and L2 views.¶

  • TenGigE0/2/0/0.100 through .300: VLAN subinterfaces in L2 and L3.¶

  • TenGigE0/1/0/0 and TenGigE0/1/0/1: physical LAG members.¶

  • Bundle-Ether10: LAG represented in L2 and L3.¶

  • TenGigE0/2/0/1 and HundredGigE0/2/0/1: inventory-only ports.¶

A.2. Interface Inventory Representation

The proposed model covers RouterB's interface inventory through one device entry keyed by its network-element reference. Under that entry, the mounted "ietf-interfaces:interfaces" subtree carries the standard interface identity, type, state, speed, IP addressing, MTU, and layering relationships. The mounted augmentation adds:¶

  • "inventory-ref" when an interface can be associated with a physical inventory port;¶

  • "topology-ref" when the interface is represented by one or more topology termination points; and¶

  • "vlan-id" and "controller-annotation" for the additional interface information defined by this proposal.¶

Appendix C. OpenConfig Comparisons

C.1. Interface Layering

The bidirectional LAG/VLAN stacking design in Section 5.1 is validated by real-world experience in OpenConfig: when openconfig-interfaces alone proved insufficient for LAG membership queries, openconfig-if-aggregate added both directions of the same relationship RFC 8343 Section 3.3 provides generically -- an aggregate interface's "aggregation/state/ member" leaf-list points down at its member interfaces, and each member's "ethernet/config/aggregate-id" leaf points back up at its aggregate -- for the specific case of LAGs. That OpenConfig had to add this reverse pointer explicitly, after the fact and for one interface type, is strong practical evidence that a generic bidirectional stacking mechanism is required at the interface-model layer. This document relies on the RFC 8343 generic mechanism instead of a LAG-specific one so that the same "higher-layer-if"/"lower-layer-if" pair also covers VLAN sub-interfaces and other interface-type stacking without a separate leaf per interface type.¶

C.2. Attribute Comparisons

The following comparisons identify related OpenConfig leaves and cases for which no direct counterpart was identified:¶

  • "inventory-ref/port-ref": openconfig-platform-port's "hardware-port" leaf provides a similar per-device binding.¶

  • "topology-ref": no stored interface-level topology reference was identified.¶

  • "vlan-id": openconfig-vlan defines "/interfaces/interface/subinterfaces/subinterface/vlan/match/ single-tagged/config/vlan-id", with the same range (1-4094).¶

  • IP addressing and per-family MTU are represented using RFC 8344 (ietf-ip) rather than as additional augmentation leaves. OpenConfig models interface IP configuration under openconfig-if-ip, and models interface MTU under openconfig-interfaces.¶

  • "controller-annotation": no counterpart was identified for this unstructured field.¶
