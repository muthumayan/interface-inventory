                    Network-wide Interface Inventory
              draft-ragalla-network-interface-inventory-00

Abstract

   This document defines a YANG data model for a network-wide inventory
   of physical and logical interfaces, organized by network element.
   The model provides interface attributes, operational state, and
   layering relationships, with correlations to network inventory and
   topology data.

1.  Introduction

   Network operators and management systems need a consistent inventory
   of physical and logical interfaces across network elements.  Such an
   inventory supports per-device retrieval of interface attributes and
   state, as well as correlation with network inventory and topology.

   An SDN controller can expose this inventory to northbound clients,
   such as higher-level controllers and automation systems, to support
   network-wide operations.

   RFC 8343 [RFC8343] defines interface data, including operational
   state and interface-layering relationships, for a server.  The IVY
   network inventory model [IVY-INVENTORY] describes network elements
   and their components, while RFC 8345 [RFC8345] and the IVY inventory
   topology model [IVY-TOPOLOGY] describe topology and its relationship
   to inventory.  These models provide complementary information.

   This document defines a network-wide interface inventory organized by
   network element.  It reuses RFC 8343 interface data and provides
   correlations to network inventory and topology.  Sections 5 and 6
   describe the data model, Section 7 describes the RESTCONF operations,
   and Appendix A provides a worked example.  Discovery and
   reconciliation of the underlying data are implementation-specific.

3.  Problem Statement

   A network management system may collect interface data from multiple
   network elements and expose it to clients.  RFC 8343 [RFC8343]
   provides an interface model for a server, including interface state
   and layering.  The IVY inventory model [IVY-INVENTORY] identifies
   network elements and components, while RFC 8345 [RFC8345] and the IVY
   inventory topology model [IVY-TOPOLOGY] describe topology and its
   relationship to inventory.

   These models do not themselves define the combined inventory view
   proposed here: interface data organized by IVY network-element
   identity, with correlations from each interface to its associated
   inventory component and topology termination points.  A client using
   the separate data sets may need to obtain and correlate information
   from device, inventory, and topology views, including multiple
   topology layers.

   For example, a controller can learn from the RFC 8345 [RFC8345]
   topology model which link connects two network devices.  If that link
   is realized as a link aggregation group (LAG) and the link degrades
   (for example, due to loss/errors on one member), troubleshooting
   typically requires identifying the member interfaces of the LAG on
   each device.  A controller may already collect the LAG and member-
   interface relationships while building its topology view, but RFC
   8345 [RFC8345] does not provide a device-scoped interface inventory
   with operational state and layering that can be retrieved and
   correlated directly to the topology termination points.  This
   document's model allows the controller to expose that per-device
   interface inventory and its correlations northbound, so clients can
   navigate from a topology link to the underlying per-device member
   interfaces and their state.

   The proposed model provides a common structure for that view.  Its
   completeness and accuracy depend on the data available to the server
   and on the server's discovery and reconciliation mechanisms.

4.  Relationship to Existing Work

   RFC 8343 [RFC8343] Section 3.3 ("Interface Layering") already defines
   the generic mechanism this document needs: two read-only leaf-lists,
   "higher-layer-if" and "lower-layer-if", present on every
   "/interfaces/interface" entry, explicitly described as the YANG
   equivalent of the IF-MIB "ifStackTable" (RFC 8343 Section 4)
   [RFC2863].  A LAG's members populate the LAG's "lower-layer-if"; each
   member's "higher-layer-if" points back at the LAG.  A VLAN sub-
   interface's "lower-layer-if" points at its parent physical interface.
   This document does not redefine LAG or VLAN semantics; it relies
   entirely on RFC 8343 Section 3.3 for interface stacking [RFC8343].

   RFC 8528 [RFC8528] ("YANG Schema Mount") defines a mechanism for
   attaching a schema tree at a mount point.  Its Appendix A illustrates
   device/LNE-scoped mounted data, but the RFC does not prescribe a
   device key or require one mount per device.  This proposal chooses
   that organization as a data-model design.  It uses separate parent
   and mounted modules.  RFC 8528 confines paths in a mounted schema to
   the mount jail; therefore the mounted augmentation represents cross-
   model inventory/topology identifiers as strings rather than leafrefs
   into parent-schema data.  A server may use shared-schema parent-
   reference metadata for XPath evaluation, but this proposal does not
   require it.  This document does not change RFC 8345 [RFC8345], RFC
   8346 [RFC8346], RFC 8944 [RFC8944], or the IVY drafts.

5.  Data Model Overview

5.1.  Design Summary

   *  "network-interface-inventory/device" is keyed by "ne-ref", a
      leafref into the IVY "network-element" list -- the same device
      identifier already used by inventory, so no new device identity
      scheme is introduced.

   *  Each "device" list entry is an RFC 8528 [RFC8528] mount point
      labeled "interfaces-root", under which the server exposes a
      mounted "ietf-interfaces:interfaces" subtree.  The server
      advertises the mounted module set in schema-mount/YANG Library
      data.

   *  Every "if:interface" entry in that mounted subtree is augmented
      (Section 6) with:

      -  an "inventory-ref" carrying the IVY port component identifier,
         when one is known, within the network element identified by the
         enclosing device's "ne-ref"; and

      -  zero or more "topology-ref" entries carrying string identifiers
         for the RFC 8345 [RFC8345] network/node/termination-point views
         corresponding to the interface; and

      -  a "vlan-id" convenience leaf populated from the corresponding
         RFC 8944 [RFC8944]-style topology attributes, so a client does
         not have to dereference "topology-ref" just to read a VLAN tag.

      -  IP addressing and per-family MTU are represented using RFC 8344
         [RFC8344] (ietf-ip) within the mounted schema set, rather than
         being duplicated as additional augmentation leaves.

   *  "higher-layer-if" and "lower-layer-if" are NOT redefined; they are
      inherited unmodified from RFC 8343 [RFC8343].  The server
      populates this operational view from device/interface data and
      available LAG/VLAN relationships; the discovery and reconciliation
      mechanism is implementation-specific.

   The following illustration shows the hierarchy and example
   correlations.  Device identifiers are abbreviated, and RouterX
   represents another network element.  Arrows indicate relationships,
   not data containment.

   network-interface-inventory
   |
   +-- device [ne-ref = RouterA] [mount point: interfaces-root]
   |   +-- interfaces ...
   |
   +-- device [ne-ref = RouterB] [mount point: interfaces-root]
   |   +-- interfaces
   |       +-- interface [Bundle-Ether10]
   |       |   +-- lower-layer-if --> TenGigE0/1/0/0
   |       |   +-- topology-ref -----> network / node / TP
   |       |
   |       +-- interface [TenGigE0/1/0/0]
   |           +-- higher-layer-if -> Bundle-Ether10
   |           +-- inventory-ref ---> port component in RouterB
   |           +-- topology-ref -----> network / node / TP
   |
   |   ...
   |
   +-- device [ne-ref = RouterX] [mount point: interfaces-root]
       +-- interfaces ...

5.3.  Augmentation Overview

   The mounted interface augmentation provides three categories of
   information:

   *  Correlation identifiers to connect per-device interface entries to
      inventory and topology views.

   *  Convenience leaves derived from topology data, so clients do not
      need to dereference topology termination points to retrieve a VLAN
      tag.

   *  Additional operational attributes and annotations not defined by
      the base interface model.  Interface capacity is available via RFC
      8343 [RFC8343] (ietf-interfaces) 'speed' (if:speed).

   Normative definitions for the augmentation are in the YANG modules in
   Section 6.  Examples are in Appendix A.  Informative comparisons and
   mappings are in Appendices B, C, and D.

      +================+==============================+
      | Node(s)        | Purpose                      |
      +================+==============================+
      | inventory-ref  | Correlate to inventory port  |
      | topology-ref   | Correlate to topology TP(s)  |
      | vlan-id        | Convenience VLAN tag         |
      | duplex-mode    | Augmented attribute          |
      | direction      | Augmented attribute          |
      | service-state  | Augmented attribute          |
      | floating       | Derived/no-topology flag     |
      | notes          | Free-text annotation         |
      +================+==============================+

6.  YANG Modules

   The modules use YANG 1.1 as defined in RFC 7950 [RFC7950] and follow
   the YANG authoring guidance in RFC 9907 [RFC9907].

   The model is split to respect RFC 8528 mount-jail semantics.  The
   parent module is loaded in the management system's parent schema.  At
   each mount point, the server advertises a mounted schema set that
   includes ietf-interfaces, ietf-ip, and device-interface-attributes.
   The same mounted module set MAY be shared by all devices when their
   schemas are identical.  The server MUST publish the applicable mount-
   point schema through RFC 8528 [RFC8528] schema-mount data and the
   YANG Library mechanism (RFC 8525 [RFC8525]).

   The mounted augmentation contains no leafref into the parent
   inventory or topology trees.  Its cross-model correlation values are
   strings: RFC 8528 confines mounted paths to the mount jail unless a
   server configures shared-schema parent-reference metadata.  This
   proposal does not require parent-reference metadata.

6.1.  Parent module: inventory-network-interfaces

   module inventory-network-interfaces {
     yang-version 1.1;
     namespace "urn:example:ns:yang:inventory-network-interfaces";
     prefix "inii";

     import ietf-yang-schema-mount { prefix yangmnt; }
     import ietf-network-inventory { prefix nei; }

     organization "Cisco Systems, Inc.";
     contact "Ramkrishna Galla <mailto:ragalla@cisco.com>";

     description
       "Parent model for a device-scoped interface inventory.
        It identifies network elements and provides an RFC 8528 mount
        point.
        The mounted schema set includes ietf-interfaces, ietf-ip, and
        device-interface-attributes.
        This module defines no HTTP API. Servers may expose data through
        NETCONF, RESTCONF, or another management interface.";

     revision 2026-11-25 {
       description
         "Initial publication revision. Uses RFC 8344 ietf-ip for IP
          addressing and per-family MTU, and RFC 8343 if:speed for
          interface capacity.";
       reference "draft-ragalla-network-interface-inventory-00";
     }

       container network-interface-inventory {
         config false;
         description
           "Network-wide interface inventory, organized by "
           + "network element.";

       list device {
         key "ne-ref";
         description
           "One entry for each network element served by this management
            system. The ne-ref leafref is resolved in the parent schema,
            outside the mounted schema jail. The server advertises the
            mounted schema through RFC 8528 schema-mount data, using an
            inline or shared-schema entry. For this read-only view, the
            schema-mount config value MUST be false. The mounted module
            set MUST include ietf-interfaces,
            ietf-ip, and device-interface-attributes.";

         leaf ne-ref {
           type leafref {
             path "/nei:network-inventory/nei:network-elements/"
                + "nei:network-element/nei:ne-id";
           }
           description
             "Identifier of the network element owning the mounted
              interface list.";
         }

         yangmnt:mount-point "interfaces-root" {
           description
             "RFC 8528 mount point for the per-device interface model.";
         }
       }
     }
   }

6.2.  Mounted augmentation: device-interface-attributes

   module device-interface-attributes {
     yang-version 1.1;
     namespace "urn:example:ns:yang:device-interface-attributes";
     prefix "edia";

     import ietf-interfaces  { prefix if; }

     organization "Cisco Systems, Inc.";
     contact "Ramkrishna Galla <mailto:ragalla@cisco.com>";

     description
       "Read-only augmentation of mounted ietf-interfaces for a
        device-scoped interface inventory. This module is loaded at the
        interfaces-root mount point in inventory-network-interfaces.
        RFC 8528 confines a mounted schema to its mount jail. Therefore,
        inventory-ref and topology-ref use strings; no leafrefs cross
        mount boundary into parent inventory or topology data.";

     revision 2026-11-25 {
       description
         "Initial publication revision. Uses RFC 8344 ietf-ip for IP
          addressing and per-family MTU, and RFC 8343 if:speed for
          interface capacity.";
       reference "draft-ragalla-network-interface-inventory-00";
     }

     grouping topology-ref {
       description
         "Reference to a termination point in an RFC 8345 topology view.
          The identifiers are strings because the referenced topology
          data may be outside the mounted schema.";

       leaf network-ref {
         type string;
         mandatory true;
         description "RFC 8345 network-id.";
       }
       leaf node-ref {
         type string;
         mandatory true;
         description "node-id within network-ref.";
       }
       leaf tp-ref {
         type string;
         mandatory true;
         description "tp-id within node-ref.";
       }
     }

     grouping inventory-ref {
       description
         "Identifies the inventory port component associated with this
          interface, within the network element identified by the
          enclosing device's ne-ref. The identifier is a string because
          IVY inventory data may be outside the mounted schema.";

       leaf port-ref {
         type string;
         description
           "IVY component-id of the physical port, when known, scoped
            to the network element identified by the enclosing device's
            ne-ref. This leaf identifies a directly associated physical
            port. A link aggregation interface has no port-ref; its
            physical ports can be identified by following its
            lower-layer-if entries to member interfaces and reading
            their port-ref values, when the server reports those
            relationships and correlations. This string does not enforce
            the existence of the referenced inventory component.";
       }
     }

     augment "/if:interfaces/if:interface" {
       description
         "Adds read-only inventory/topology correlations and commonly
          needed interface attributes to the mounted RFC 8343 interface
          list. IP addressing and per-family MTU use RFC 8344 ietf-ip
          when that module is in the mounted schema set. The base
          ietf-interfaces module remains unchanged.";

       container inventory-ref {
         config false;
         description
           "Correlation to a physical port component, if one is known.";
         uses inventory-ref;
       }

       list topology-ref {
         config false;
         key "network-ref node-ref tp-ref";
         description
           "Zero or more topology termination points for this interface.
            An interface in multiple topology layers has one entry per
            layer or view.";
         uses topology-ref;
       }

       leaf vlan-id {
         config false;
         type uint16 { range "1..4094"; }
         description "Outer VLAN identifier when applicable.";
         reference
           "RFC 8944; openconfig-vlan single-tagged vlan-id";
       }
       leaf duplex-mode {
         config false;
         type enumeration {
           enum full-duplex;
           enum half-duplex;
           enum auto;
         }
         description
           "Observed/configured duplex state. The auto value is a
            convenience rollup; OpenConfig models auto-negotiation as a
            separate boolean.";
         reference
           "RFC 3635 EtherLike-MIB; openconfig-if-ethernet";
       }

       leaf direction {
         config false;
         type enumeration {
           enum in;
           enum out;
           enum bidir;
         }
         description "Signal direction where applicable.";
       }
       leaf service-state {
         config false;
         type enumeration {
           enum planned;
           enum in-test;
           enum in-service;
           enum maintenance;
           enum out-of-service;
         }
         description
           "Service/lifecycle state, distinct from RFC 8343 admin-status
            and oper-status.";
       }

       leaf floating {
         config false;
         type boolean;
         description
           "True when topology-ref is empty. inventory-ref may still
            identify a physical component outside topology.";
       }

       leaf notes {
         config false;
         type string;
         description "Optional human-readable annotation.";
       }
     }
   }

7.  RESTCONF Operations

   These examples use the RESTCONF URI form defined by RFC 8040
   [RFC8040] for a resource beneath a schema-mount point.  They assume
   the parent and mounted schemas described in Section 6 are advertised
   by the server through schema-mount/YANG Library data.
   Implementations that do not expose RESTCONF may provide equivalent
   data through another API.

7.1.  Retrieve All Interfaces on a Device

   A client retrieves every interface on a device with a single GET
   against the mounted interfaces container.  URI path key values MUST
   be percent-encoded when they contain reserved characters:

      GET /restconf/data/inventory-network-interfaces:\
          network-interface-inventory/\
          device=RouterB.subdomain1.region3.bt.uk/\
          ietf-interfaces:interfaces

   The response representation is the mounted "ietf-
   interfaces:interfaces" subtree plus augmentation data.  The requested
   device key supplies the network-element context for any "inventory-
   ref/port-ref" in that subtree.  Appendix A.1 shows a shortened full
   parent data-tree fixture for context; it is not the literal body of
   this subtree GET.

7.2.  Retrieve a Single Interface

      GET /restconf/data/inventory-network-interfaces:\
          network-interface-inventory/\
          device=RouterB.subdomain1.region3.bt.uk/\
          ietf-interfaces:interfaces/\
          interface=Bundle-Ether10

7.3.  Filtering by Interface Type

   RESTCONF does not define generic server-side predicate filtering on
   list entries.  The base operation in this document returns the
   interface list; RFC 8040 [RFC8040] "fields" and "depth" may be used
   for payload selection.  A future revision MAY specify a YANG action
   or another explicit filter contract for high-interface-count devices;
   no such action or filter is defined by this revision.

7.4.  Protocol Buffers Encoding for Streaming Clients

   RESTCONF/JSON (RFC 7951 [RFC7951]) is the canonical encoding for this
   document's data model, but some clients -- in particular gRPC- based
   telemetry and streaming consumers -- prefer a typed binary wire
   format.  A non-normative Protocol Buffers (proto3) schema,
   "inventory-network-interfaces.proto", is published alongside this
   document.

   Relationship to gNMI.  gNMI (gRPC Network Management Interface, gRPC-
   based model-agnostic subscribe/get for YANG-modeled data) is an
   established streaming option for this data model [GNMI].  Clients may
   subscribe to the mounted ietf-interfaces subtree with gNMI; the
   service-specific proto is an alternative for clients that want
   strongly typed messages without gNMI's generic "TypedValue" and path-
   oriented API.  It is optional and does not replace gNMI or the
   RESTCONF operations in Sections 7.1-7.3.

   The proto schema defines:

   *  "Interface", "Device", and "DeviceInterfaces" messages that
      represent data from both YANG modules in Section 6.  The proto
      uses snake_case names and includes helper fields such as
      "type_name" for IANA values outside its finite enum; the proto
      comments document the mapping.  "Ipv4" and "Ipv6" carry the per-
      family addresses and MTU from RFC 8344 [RFC8344];

   *  enum types for "InterfaceType", "AdminStatus", "OperStatus",
      "DuplexMode", "Direction", and "ServiceState", plus "EventType"
      for the event stream;

   *  a unary "NetworkInterfaceInventory.GetDeviceInterfaces" RPC,
      equivalent to the RESTCONF GET in Section 7.1;

   *  a paginated "ListDeviceInterfaces" RPC that returns
      "ListDeviceInterfacesResponse" with "device" entries plus a
      "next_page_token", for clients iterating over a very large fleet;
      and

   *  a server-streaming "StreamDeviceInterfaceEvents" RPC that pushes a
      "DeviceInterfaceEvent" (create / update / delete / initial
      snapshot, with a timestamp and optional "changed_fields") per
      interface event.  For DELETE, "interface" carries the last-known
      pre-delete snapshot; initial synchronization uses the distinct
      SNAPSHOT event type.

   The protobuf schema is informative.  Its field naming and helper enum
   fields are not a normative wire encoding of YANG; the YANG modules in
   Section 6 are authoritative if the representations differ.  The proto
   carries the device key once on "Device.ne_ref";
   "Interface.inventory_ref" contains only the port component
   identifier.

8.  Security Considerations

   The parent device list exposes device identifiers and interface
   inventory relationships.  Implementations MUST apply authorization to
   both the parent device list and every mounted interface schema.
   Access control on a parent data node does not by itself establish the
   same policy for mounted data.  Servers MUST configure and test access
   control for mounted instances in accordance with RFC 8528 and the
   Network Configuration Access Control Model (NACM, RFC 8341
   [RFC8341]).

   The YANG augmentation modules defined here are operational/read-only
   (their added nodes are config false).  The mounted ietf-interfaces
   schema itself contains both configuration and operational-state
   nodes; this document does not claim that the whole mounted schema is
   config false.  A GET-only facade MUST reject write methods unless a
   separate write contract and authorization policy are specified.

   Interface identifiers, topology relationships, and device inventory
   can be sensitive network information.  Implementations SHOULD limit
   access by user, tenant, and device scope, protect RESTCONF/API
   transport with TLS, and apply equivalent authorization to streamed
   events and unary reads.

10.  Appendix A.  Full Worked Example (mobilecore.region3)

   The complete source data used to ground Appendix A.1 -- three IOS XR

   mounted-subtree response is derived -- are published as a companion
   file set:

   *  examples/mobilecore-region3/01-ivy-network-inventory.json

   *  examples/mobilecore-region3/02-ivy-inventory-topology.json

   *  examples/mobilecore-region3/03-l2-topology.json

   *  examples/mobilecore-region3/04-l3-topology.json

   *  examples/mobilecore-region3/05-network-interface-schema-mount-
      v4.json

   *  inventory-network-interfaces@2026-11-25.yang (parent module)

   *  device-interface-attributes@2026-11-25.yang (mounted module)

   *  inventory-network-interfaces.proto (Section 7.4)

   The YANG modules, protobuf schema, source topology payloads, and
   worked JSON fixture are included in this repository.  The JSON
   fixture is a synthetic example; interface state/MAC/ifIndex values
   not present in the source topology payloads are illustrative, not
   live-device observations.

   The topology payloads describe the following three-router
   connectivity.  RouterA, RouterB, and RouterC are shorthand for the
   corresponding *.subdomain1.region3.bt.uk node identifiers in the
   fixture.

                            RouterA
                           /       \
                          /         \
       VLAN 100/200/300  /           \ 100G physical link
       TenGigE0/2/0/0   /             \ HundredGigE0/2/0/0
                       /               \
                  RouterB =============== RouterC
                          Bundle-Ether10
                            (LAG)
                Members at each end: TenGigE0/1/0/0 and
                                     TenGigE0/1/0/1

   RouterB inventory-only ports: TenGigE0/2/0/1 and HundredGigE0/2/0/1
   (no topology TP/link).

   The RouterA-to-RouterB connection has VLAN subinterfaces 100, 200,
   and 300 over the physical TenGigE port.  RouterB and RouterC connect
   through the Bundle-Ether10 LAG; the two member links are shown below
   it.  RouterA and RouterC have a direct HundredGigE link.

   RouterB's interfaces are represented as follows in the source
   inventory and topology data:

   *  TenGigE0/2/0/0: physical interface in the physical and L2 views.

   *  TenGigE0/2/0/0.100 through .300: VLAN subinterfaces in L2 and L3.

   *  TenGigE0/1/0/0 and TenGigE0/1/0/1: physical LAG members.

   *  Bundle-Ether10: LAG represented in L2 and L3.

   *  TenGigE0/2/0/1 and HundredGigE0/2/0/1: inventory-only ports.

11.  Appendix B.  Comparison Against Commonly Implemented Interface
     Attributes

   The attributes were compared with commonly implemented IF-MIB-based
   interface inventories.  No specific product or API is referenced.

   *  RFC 8343 [RFC8343] covers interface name, description, type,
      administrative and operational status, ifIndex, physical address,
      speed, and link-up/down trap enable.

   *  RFC 8344 [RFC8344] provides IP addresses and per-family MTU.

   *  Section 6 adds duplex mode, signal direction, service state, and a
      flag for interfaces without topology references.

   *  Separate connector/equipment identifiers, connector presence,
      promiscuous and SPAN/RSPAN flags, internal location indexes, soak
      timers, supported MTU ranges, shared-risk group IDs, entity-alias
      mappings, LAG end identifiers, and alias names are deferred.
      inventory-ref/port-ref identifies a port but does not distinguish
      it from its connector or associated equipment.

12.  Appendix C.  OpenConfig Comparisons

12.1.  Interface Layering

   The bidirectional LAG/VLAN stacking design in Section 5.1 is
   validated by real-world experience in OpenConfig [OC-AGGREGATE]: when
   openconfig-interfaces alone proved insufficient for LAG membership
   queries, openconfig-if-aggregate added both directions of the same
   relationship RFC 8343 Section 3.3 provides generically -- an
   aggregate interface's "aggregation/state/ member" leaf-list points
   down at its member interfaces, and each member's "ethernet/config/
   aggregate-id" leaf points back up at its aggregate -- for the
   specific case of LAGs.  That OpenConfig had to add this reverse
   pointer explicitly, after the fact and for one interface type, is
   strong practical evidence that a generic bidirectional stacking
   mechanism is required at the interface-model layer.  This document
   relies on the RFC 8343 [RFC8343] generic mechanism instead of a LAG-
   specific one so that the same "higher-layer-if"/"lower-layer-if" pair
   also covers VLAN sub-interfaces and other interface-type stacking
   without a separate leaf per interface type.

12.2.  Attribute Comparisons

   The following comparisons identify related OpenConfig leaves and
   cases for which no direct counterpart was identified:

   *  "inventory-ref/port-ref": openconfig-platform-port's "hardware-
      port" leaf provides a similar per-device binding
      [OC-PLATFORM-PORT].

   *  "topology-ref": no stored interface-level topology reference was
      identified.

   *  "vlan-id": openconfig-vlan defines
      "/interfaces/interface/subinterfaces/subinterface/vlan/match/
      single-tagged/config/vlan-id", with the same range (1-4094)
      [OC-VLAN].

   *  IP addressing and per-family MTU are represented using RFC 8344
      (ietf-ip) rather than as additional augmentation leaves.
      OpenConfig models interface IP configuration under openconfig-if-
      ip, and models interface MTU under openconfig-interfaces
      [OC-IF-IP] [OC-INTERFACES].

   *  "duplex-mode": openconfig-if-ethernet defines
      "/interfaces/interface/ethernet/config/duplex-mode" with FULL and
      HALF values, and models auto-negotiation separately with "auto-
      negotiate".  This document's "auto" value is a convenience for
      servers that have not yet resolved a negotiated duplex
      [OC-ETHERNET].

   *  "direction": no single generic leaf was identified.  A related
      concept is the client/line role in an openconfig-terminal-device
      logical-channel-assignments entry for optical transport
      [OC-TERMINAL-DEVICE].

   *  "service-state": no interface-scoped counterpart was identified.

   *  "floating": no equivalent boolean was identified.  An absent
      openconfig-platform-port "hardware-port" indicates no port
      binding; it does not establish whether an interface has topology
      references [OC-PLATFORM-PORT].

   *  "notes": no counterpart was identified for this unstructured
      field.

13.  Appendix D.  SNMP MIB Object Mapping (Informative)

   This informative mapping gives related SNMP objects where a close
   analogue exists.  It does not constrain implementations.

   *  inventory-ref: ENTITY-MIB entAliasMappingTable [RFC6933].

   *  higher-layer-if and lower-layer-if: IF-MIB ifStackTable [RFC2863].

   *  vlan-id: Q-BRIDGE-MIB dot1qVlan objects [RFC4363].

   *  duplex-mode: EtherLike-MIB dot3StatsDuplexStatus [RFC3635].

   *  IP addresses: IP-MIB ipAddressTable [RFC4293].

   *  No close SNMP object was identified for topology-ref, direction,
      service-state, floating, or notes.
